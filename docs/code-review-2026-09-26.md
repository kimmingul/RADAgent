# RAD Agent 소스 코드 검토 보고서

## 검토 기준과 사용 방법

- 검토일: 2026-09-26.
- 기준 소스: `666bbc3342d0c11a407362306cfacc36ddce3f2f`.
- 대상: Delphi 패키지 소스, 채팅 JavaScript/HTML/CSS, 설정·언어 리소스, LSP 연결, 빌드·설치·서명 스크립트, 관련 테스트와 배포 설정.
- 목적: 오류가 발생하는 조건과 코드 경로를 정리하여 후속 설계·수정 논의에 사용한다. 개선 방향은 제안이며 구현 확정안이 아니다.
- 결과: 앱 동작 관련 28건과 개발 스크립트 관련 2건. 단순 스타일·명명·리팩터링 제안은 제외했다.
- 검토 과정에서는 소스 수정, 빌드, 설치, IDE 실행·조작, 레지스트리 변경을 하지 않았다. 이 문서는 검토 후 별도로 작성한 기록이다.
- 파일 링크의 줄 번호는 위 기준 소스에 해당한다. 이후 수정되면 줄 번호보다 함수명과 오류 조건을 우선한다.
- 모든 항목은 이 보고서 기준으로 미수정이다. 기존 빌드·테스트 성공은 아래 경로의 안전성을 증명하지 않는다.

### 증거 수준

- **국소 재현**: 실제 JavaScript 파일을 메모리 내 fixture에서 실행하거나, 격리된 임시 Git 저장소에서 앱과 같은 명령을 실행해 결과를 확인했다. 실제 IDE를 통한 종단 간 재현은 아니다.
- **정적 분석 [INFERENCE]**: 소스의 호출·상태 전이와 필요한 ToolsAPI/RTL 계약을 추적했다. 해당 장애를 실제 IDE에서 발생시키지 않았으므로 발생 빈도와 최종 증상은 후속 검증이 필요하다.
- 수치 계산이나 조건식 대조만 한 항목은 실제 기능을 실행한 재현으로 분류하지 않았다.
- 아래의 **검증 시나리오**는 향후 수정 전후에 실행할 제안이며, 이미 실행했다는 뜻이 아니다.

### 우선순위

- **P1**: 승인 경계 위반, 사용자 데이터 손실·잘못된 대상 변경, IDE 충돌 가능성, 정상 대화 진행을 막는 연결·수명 문제. 우선 조사·수정 권장.
- **P2**: 특정 조건의 기능 실패, 불완전한 복원·진단·표시, 개발 도구의 경로 처리 문제.
- P1은 01–13, P2는 14–30이다. 우선순위는 영향도 기준이며 재현 여부나 발생 빈도와 동일하지 않다.

## P1 — 우선 조사·수정할 항목

### 01. 승인 요청의 내용이 IDE 도구 예외 처리로 오인됨

- **근거**: 정적 분석 [INFERENCE]. [ChatCommand:346–351](../src/RADAgent.ChatCommand.pas#L346), [AskDialog:287–294](../src/RADAgent.AskDialog.pas#L287).
- **발생 조건**: 일반 파일 쓰기 승인 요청의 본문에 `xd://rad.compile` 같은 문자열이 포함된다. 예를 들어 `C:\Project\notes.txt`에 IDE 도구 사용 예제를 기록하는 요청이다.
- **원인**: `ApprovalTargetsRad`는 실제 대상 대신 `Ui.Title + Ui.Message` 전체에서 `xd://rad.`를 검색한다. omp 승인 설명에는 쓰려는 내용도 포함될 수 있다. `ExtensionReply`는 이 결과를 근거로 자동 승인하며, `PlanActive`의 거부 분기보다 먼저 실행한다.
- **영향**: IDE 도구가 아닌 일반 쓰기가 사용자 확인 없이 승인된다. 계획 모드에서도 변경 금지 의도를 우회할 수 있다. 조건식 대조에서도 일반 파일을 대상으로 하는 예제 요청이 True로 분류됐다.
- **개선 방향**: 신뢰할 수 있는 도구·대상 필드를 기준으로 분류한다. 해당 RPC 계약에 구조화된 필드가 없으면 정확한 대상 영역만 보수적으로 해석하고, 불명확한 요청은 자동 승인하지 않는다. 인자·본문 문자열을 승인 근거로 사용하지 않는다.
- **검증 시나리오**: 항상 묻기와 계획 모드 각각에서 일반 파일 내용에 `xd://rad.*`를 포함시킨다. 전자는 승인을 요구하고 후자는 거부해야 한다. 실제 IDE 도구 호출의 중복 승인 제거도 별도로 확인한다.

### 02. 문장 기반 체크포인트 연결로 다른 시점의 파일이 복원됨

- **근거**: 국소 재현. [checkpoints.js:41–59](../src/chat/checkpoints.js#L41), [ChatCheckpoints:108–116](../src/RADAgent.ChatCheckpoints.pas#L108), [ChatCheckpoints:209–214](../src/RADAgent.ChatCheckpoints.pas#L209).
- **발생 조건**: 같은 저장소의 서로 다른 세션 또는 동일 세션의 여러 위치에서 같은 문장을 보낸 뒤 대화를 다시 불러오거나 이전 메시지로 되돌린다.
- **원인**: 전체 저장소의 체크포인트를 세션 ID 없이 나열하고 문장·접두사로 연결한다. 대화의 분기 대상도 문장이 일치하는 마지막 엔트리로 선택한다. 파일 복원 대상과 대화 분기 대상의 고유 식별이 없다.
- **영향**: 세션 A의 메시지에 세션 B의 체크포인트가 붙어 잘못된 파일 상태를 복원한다. 같은 문장이 반복되면 의도한 메시지보다 뒤에서 대화가 갈라질 수도 있다.
- **재현 결과**: 실제 `checkpoints.js`에 세션 A의 단일 `Fix build` 메시지와 번호 1·2의 동일 문장 체크포인트를 넣었다. A의 기대값은 1이지만 `dataset.seq`는 `2`가 됐다.
- **개선 방향·검증**: 저장소·세션·메시지 엔트리 ID와 체크포인트 커밋을 명시적으로 연결한다. ID가 없는 과거 기록은 추측 복원을 피한다. 동일 문장 반복, 접두사가 같은 문장, 세션 전환, 첨부·선택 영역 포함 요청에서 파일과 대화가 같은 시점을 가리키는지 검증한다.

### 03. 캐럿 삽입이 승인받은 편집기와 다른 편집기에 적용됨

- **근거**: 정적 분석 [INFERENCE]. [BufferEdits:34–55](../src/RADAgent.BufferEdits.pas#L34), [ChatApprovalCard:140–147](../src/RADAgent.ChatApprovalCard.pas#L140).
- **발생 조건**: UnitA에서 `rad.insert_at_caret`의 채팅 승인을 기다리다가 UnitB로 이동한 뒤 승인한다. 같은 파일에서 캐럿만 옮긴 경우도 위치가 바뀐다.
- **원인**: 승인 전에는 `CurrentEditorText`로 대상 파일을 읽지만, 승인 후 현재 `TopView`를 다시 가져온다. 승인 대기 루프는 IDE 메시지를 처리하므로 그 사이 편집기·위치 변경이 가능하다.
- **영향**: UnitB에 코드가 삽입되는데 `ChangeApplied`는 UnitA라고 알린다. 이어지는 프로젝트 저장으로 잘못된 편집이 디스크에 반영된다.
- **개선 방향**: 승인 대상 버퍼·삽입 위치·관련 버전을 명시적으로 고정하고 승인 후 재검증한다. 파일이 닫히거나 내용·대상이 바뀌면 취소 또는 재승인을 요구한다.
- **검증 시나리오**: 승인 대기 중 다른 파일 이동, 캐럿 이동, 원래 파일 수정·닫기를 각각 수행한다. 승인 내용과 다른 파일·위치에 삽입되지 않고 알림의 대상도 실제 변경과 일치해야 한다.

### 04. 폼 텍스트 승인 대기 중 발생한 사용자 변경을 덮어씀

- **근거**: 정적 분석 [INFERENCE]. [FormText:225–250](../src/RADAgent.FormText.pas#L225).
- **발생 조건**: `rad.form_text_edit` 승인 카드가 나온 뒤 사용자가 같은 폼의 속성을 수정·저장하고 승인한다. 디자이너·소스에 저장하지 않은 변경이 남는 경우도 점검 대상이다.
- **원인**: `Prepare`가 승인 전에 계산한 `Item.After`를 승인 후 바로 기록한다. 디스크 스냅샷과 모듈의 수정 상태를 재검사하지 않고 `Module.Refresh(True)`를 호출한다.
- **영향**: 승인 대기 중 저장한 사용자 변경이 이전 스냅샷으로 덮인다. 저장하지 않은 편집도 강제 다시 읽기의 대상이 된다.
- **개선 방향**: 적용 직전에 디스크 내용·모듈 수정 상태·프로젝트 정체성을 검사한다. 충돌이면 덮어쓰지 않는다. 여러 폼을 수정하는 요청은 일부 파일만 적용된 상태의 처리 방식도 명시해야 한다.
- **검증 시나리오**: 승인 대기 중 같은 속성 또는 다른 속성을 수정하고 저장한 경우 모두 사용자 변경을 보존해야 한다. 외부 디스크 변경과 다중 파일 중 한 파일만 충돌하는 경우도 포함한다.

### 05. 저장 실패를 무시하고 프롬프트·도구 성공 처리를 계속함

- **근거**: 정적 분석 [INFERENCE]. [ChatActions:63–80](../src/RADAgent.ChatActions.pas#L63), [ChatActions:332–336](../src/RADAgent.ChatActions.pas#L332), [ChatDiskSync:28–34](../src/RADAgent.ChatDiskSync.pas#L28).
- **발생 조건**: 파일이 읽기 전용이거나 저장이 거절·취소·실패한 상태에서 메시지를 보내거나 IDE 변경 도구를 사용한다.
- **원인**: `SaveProject`는 Boolean을 반환하지만 일반 전송, 큐 전송, IDE 변경 후 저장 경로에서 결과를 사용하지 않는다. 경고만 표시한 뒤 계속 진행한다.
- **영향**: omp는 IDE와 다른 오래된 디스크 내용을 기준으로 작업한다. 체크포인트도 실제 IDE 상태를 담지 못한다. IDE 도구는 디스크 반영 실패를 성공 결과와 구분하지 않아 다음 도구가 잘못된 전제에서 실행된다.
- **개선 방향**: 프롬프트 전 저장 실패는 전송을 차단하고 입력을 보존한다. 이미 적용한 IDE 변경의 저장 실패는 성공과 구분해 전달하되, 사용자 편집을 임의로 롤백하지 않는다. `FormText`의 별도 저장 호출도 함께 점검한다.
- **검증 시나리오**: 저장 실패를 주입하여 일반·steer·follow-up 전송이 차단되는지 확인한다. 변경 도구 적용 후 저장 실패에서는 실제 버퍼 상태와 오류 결과가 일치해야 한다.

### 06. 기존 프로젝트 LSP 설정을 통째로 덮어씀

- **근거**: 정적 분석 [INFERENCE]. [OmpLaunch:84–109](../src/RADAgent.OmpLaunch.pas#L84), [CppLsp:207–221](../src/RADAgent.CppLsp.pas#L207).
- **발생 조건**: 프로젝트 `.omp/lsp.json`에 다른 서버나 사용자 옵션이 있는 상태에서 RAD Agent가 LSP 설정을 준비한다.
- **원인**: 파일을 읽어 병합하지 않고 새 객체에 `delphilsp` 또는 `clangd` 하나만 만든 뒤 전체 파일에 기록한다. 이 경로는 RAD Agent 전용 임시 파일이 아니라 omp가 읽는 프로젝트 설정이다.
- **영향**: 다른 서버, 비활성화 플래그, 사용자 인자와 시간 제한 설정 등이 사라진다. 사용자 도구 구성이 다음 실행부터 달라질 수 있다.
- **개선 방향**: RAD Agent가 소유할 설정 범위를 정하고 나머지를 보존한다. 기존 동일 서버 항목을 사용자가 수정한 경우의 우선순위도 결정한다. 깨진 JSON을 빈 설정으로 간주해 덮어쓰지 않는다.
- **검증 시나리오**: 여러 서버·사용자 옵션을 둔 설정에서 Delphi와 C++ 준비를 반복한다. 소유하지 않은 값이 유지되고 반복 실행 결과가 안정적이어야 한다.

### 07. WebView2 생성 완료 콜백이 해제된 호스트를 호출할 수 있음

- **근거**: 정적 분석 [INFERENCE]. [WebView2Host:102–110](../src/RADAgent.WebView2Host.pas#L102), [WebView2Host:168–183](../src/RADAgent.WebView2Host.pas#L168), [WebView2Handlers:67–81](../src/RADAgent.WebView2Handlers.pas#L67).
- **발생 조건**: WebView2 환경·컨트롤러를 비동기로 만드는 동안 데스크톱 전환 등으로 채팅 프레임과 호스트가 파괴된다.
- **원인**: COM 핸들러가 호스트의 raw object-method 포인터를 보관하고 무조건 호출한다. 호스트 소멸자는 대기 중 완료 핸들러를 무효화하지 않는다. 콜백 안의 `csDestroying` 검사도 이미 해제된 객체를 읽는 경우에는 보호가 되지 않는다.
- **영향**: 늦게 도착한 완료 콜백이 해제된 메모리를 접근하여 IDE 접근 위반을 일으킬 수 있다.
- **개선 방향**: 호스트와 독립적으로 수명이 유지되는 취소·수명 토큰을 사용하거나 완료 핸들러의 대상을 소멸 전에 안전하게 끊는다. 컨트롤러가 늦게 생성된 경우에도 해제 책임을 유지한다.
- **검증 시나리오**: 완료 콜백을 지연시킨 상태에서 호스트를 파괴한 뒤 완료시킨다. 해제된 객체를 호출하지 않아야 한다. 실제 IDE의 도킹·데스크톱 전환으로도 검증한다.

### 08. clangd 다운로드 작업이 BPL 해제보다 오래 살아남을 수 있음

- **근거**: 정적 분석 [INFERENCE]. [ClangdInstall:121–139](../src/RADAgent.ClangdInstall.pas#L121).
- **발생 조건**: 설정에서 clangd 설치를 시작한 뒤 다운로드가 끝나기 전에 RAD Agent 패키지를 내린다. 설정 창을 닫는 것과 패키지 해제는 별개 조건이다.
- **원인**: 익명 스레드 참조를 보관하지 않고 종료 시 join·취소하지 않는다. 완료 콜백도 `TThread.Queue(nil, ...)`로 등록하여 작업 소유자에 따른 제거가 없다.
- **영향**: BPL이 언로드된 뒤 작업 스레드나 완료 콜백이 해당 패키지 코드를 실행할 수 있다. 완료 콜백은 설정과 `ChatSession`에도 접근한다.
- **개선 방향**: 작업 소유자를 두고 다운로드 취소·종료 대기·대기 콜백 제거를 패키지 종료 순서에 포함한다. 네트워크 타임아웃과 종료 시 대기 상한도 함께 정한다.
- **검증 시나리오**: 지연되는 다운로드와 완료 직전 큐 대기를 각각 만든 뒤 패키지를 해제한다. 해제 이후 패키지 코드가 실행되지 않고 IDE 종료가 무한 대기하지 않아야 한다.

### 09. 언어 사전 교체와 백그라운드 조회가 동기화되지 않음

- **근거**: 정적 분석 [INFERENCE]. [Lang:58–75](../src/RADAgent.Lang.pas#L58), [Lang:112–114](../src/RADAgent.Lang.pas#L112), [Lang:142–152](../src/RADAgent.Lang.pas#L142).
- **발생 조건**: RPC 재시도·모델 대체 이벤트 또는 호환성 검사에서 `Tr`/`TrF`를 사용하는 동안 사용자가 화면 언어를 바꾼다.
- **원인**: 메인 스레드는 `GTable`을 Clear 후 재구성하고 백그라운드 스레드는 같은 사전을 조회한다. 일반 `TDictionary`의 변경·조회 사이에 잠금이나 안전한 스냅샷 수명 관리가 없다.
- **영향**: 해제·교체 중인 사전 내부 배열 접근으로 접근 위반 또는 이벤트 누락 가능성이 있다. 실행 중 언어를 바꾸는 타이밍에 따라 나타나므로 단순 언어 표시 검사로는 발견하기 어렵다.
- **개선 방향**: 모든 조회와 교체를 같은 동기화 정책으로 보호하거나, 불변 사전을 안전한 소유권으로 게시한다. `EnsureLoaded`, `HasKey`, 페이지 문자열 열거까지 같은 정책을 적용한다.
- **검증 시나리오**: 여러 스레드의 반복 조회와 언어 교체를 동시에 실행한다. 실제 IDE에서 응답·재시도 이벤트 수신 중 언어 변경도 확인한다.

### 10. 1MiB를 넘는 송신 프레임을 버리고 성공으로 처리함

- **근거**: 정적 분석 [INFERENCE] 및 크기 계산. [RpcClient:134–158](../src/RADAgent.RpcClient.pas#L134), [RpcClient:356–367](../src/RADAgent.RpcClient.pas#L356), [ChatExtensions:167–175](../src/RADAgent.ChatExtensions.pas#L167).
- **발생 조건**: 각각 허용 크기인 600KiB 이미지 두 장을 첨부한다. Base64 데이터만 `2 × 819,200 = 1,638,400`바이트로 1,048,576바이트 제한을 넘는다. 큰 도구 결과도 같은 경로에 들어간다.
- **원인**: `WriteFrame`은 크기 초과 또는 쓰기 실패 시 반환값 없이 종료한다. `SendPrompt`는 프레임 생성 성공을 전송 성공으로 반환한다.
- **영향**: omp에는 요청이 전달되지 않지만 사용자 메시지는 기록되고 입력창은 비워지며 Busy 상태가 된다. 도구 결과가 버려지면 omp 쪽 호출도 완료되지 못한다.
- **개선 방향**: 직렬화된 전체 프레임 크기를 사전에 검사하고 전송 성공·실패를 호출자에게 전달한다. 입력·첨부를 보존한다. 송신 chunk 지원은 현재 RPC 계약을 확인한 뒤 결정하며 수신 v2 지원만으로 송신 지원을 가정하지 않는다.
- **검증 시나리오**: 여러 이미지의 합산 크기, 긴 UTF-8 메시지, 제한 직전·초과 프레임, 끊어진 파이프, 큰 도구 결과를 확인한다. 거절된 전송은 성공 표시나 Busy 전이를 만들지 않아야 한다.

### 11. omp 종료 후 연결 상태와 프로세스 식별자가 유지됨

- **근거**: 정적 분석 [INFERENCE]. [RpcClient:251–268](../src/RADAgent.RpcClient.pas#L251), [ChatSession:208–215](../src/RADAgent.ChatSession.pas#L208), [ChatSession:251–266](../src/RADAgent.ChatSession.pas#L251).
- **발생 조건**: ready 이후 omp가 비정상 종료되거나 stdout이 끝난다.
- **원인**: `ReadLoop` 종료는 `FLinkError`와 상태 콜백만 갱신한다. `FReady`, `FHostToolsSent`, `FPid`가 남으므로 `Connected`는 True이고 재시작 조건도 성립하지 않는다.
- **영향**: 실제 자식이 없어도 메시지를 접수한다. 끊어진 파이프 쓰기 실패도 10번 경로에서 성공처럼 처리하여 대화가 대기 상태에 남는다.
- **개선 방향**: 메인 스레드에서 명시적인 연결 종료 전이를 수행하고 프로세스·파이프·활성 요청 상태를 정리한다. 재연결 정책과 사용자에게 실패를 알리는 정책을 분리한다.
- **검증 시나리오**: idle·스트리밍·도구 대기 중 자식을 종료한다. 즉시 연결 상태가 바뀌고 이후 입력이 유실되지 않아야 한다. 종료 콜백 자체가 재시작이나 객체 해제와 충돌하지 않아야 한다.

### 12. 이전 프로세스의 큐 콜백이 새 세션에서 실행될 수 있음

- **근거**: 정적 분석 [INFERENCE]. [RpcClient:169–183](../src/RADAgent.RpcClient.pas#L169), [RpcClient:316–354](../src/RADAgent.RpcClient.pas#L316).
- **발생 조건**: host-tool 요청·응답·이벤트를 메인 스레드 큐에 넣은 직후 프로젝트를 전환하거나 omp를 강제 재시작한다.
- **원인**: `Queue(nil, ...)` 콜백은 `FAlive`만 검사한다. Stop/Start는 같은 객체를 재사용하며 `FAlive`는 계속 True다. 콜백 제거 또는 프로세스 세대 검사가 없고, reader 종료 대기가 모든 큐 콜백 배출을 보장하지 않는다.
- **영향**: 이전 요청이 현재 `ChatSession`과 ToolsAPI 상태를 사용하여 새 프로젝트에 적용될 수 있다. 이전 응답·이벤트가 새 세션의 상태를 오염시킬 수도 있다.
- **개선 방향**: 프로세스 시작마다 세대 ID를 부여하고 모든 큐 작업과 응답에 캡처한다. 종료를 시작할 때 먼저 해당 세대를 무효화하고 실행 직전에 일치 여부를 검사한다.
- **검증 시나리오**: 메인 큐 처리를 지연시켜 old host call·상태 응답·종료 이벤트를 쌓고 새 프로세스를 시작한 뒤 배출한다. 어느 것도 새 프로젝트·상태를 변경하지 않아야 한다.

### 13. 셸 실행 중 재시작하면 입력 차단 상태가 남음

- **근거**: 정적 분석 [INFERENCE]. [ChatQueue:59–77](../src/RADAgent.ChatQueue.pas#L59), [ChatQueue:91–107](../src/RADAgent.ChatQueue.pas#L91), [composer.js:263–267](../src/chat/composer.js#L263).
- **발생 조건**: 긴 `!command` 실행 중 승인 드롭다운을 바꾸거나 다른 디렉터리의 프로젝트로 전환한다. 셸 실행 중에는 일반 composer 제출이 막히므로 `/restart` 입력보다 이 경로로 검증해야 한다.
- **원인**: `GShell`은 실행 시작 시 True, 기존 자식의 `bash` 응답을 처리하는 `ShowBash`에서만 False가 된다. 재시작 판단은 agent Busy를 사용하고 셸 상태를 별도로 정리하지 않는다.
- **영향**: 기존 자식이 응답 전에 종료되면 새 세션에도 `GShell=True`가 남는다. 일반 입력이 계속 거부되고 Stop의 `abort_bash` 요청으로도 이 플래그가 해제되지 않는다.
- **개선 방향**: 셸 요청 상태를 프로세스·세션 소유로 만들고 종료·전환·실패에서 반드시 해제한다. 이전 자식의 늦은 응답이 새 셸 상태를 해제하지 않도록 12번의 세대 검사와 연결한다.
- **검증 시나리오**: 셸 실행 중 승인 변경, 프로젝트 전환, 자식 종료를 수행한다. 새 세션에서 메시지와 다음 셸 명령을 정상 제출할 수 있어야 한다.

## P2 — 추가 동작 오류

### 14. 체크포인트 복원이 불완전해도 성공으로 표시됨

- **근거**: 국소 재현. [GitRepo:212–225](../src/RADAgent.GitRepo.pas#L212).
- **발생 조건·원인**: 복원 대상 이후 이름이 바뀐 파일은 rename 감지 시 `R`로 분류되어 `--diff-filter=A` 삭제 목록에서 빠진다. 새 파일 삭제에 사용하는 `DeleteFile`의 실패 반환값도 무시한다.
- **재현 결과**: `diff.renames=true`인 임시 저장소에서 `Old.pas`를 `New.pas`로 바꾸고 동일 복원 명령을 실행했다. diff는 `R100`, 삭제 후보는 빈 목록이었으며 복원 뒤 두 파일이 모두 남았다. 별도 시험에서 추가 파일을 삭제 불가로 열어 두자 Windows 오류 32가 발생했지만 뒤의 Git 명령은 종료 코드 0이고 파일도 남았다.
- **영향**: 되돌리기 성공 알림과 실제 파일 트리가 다르다. 중복 유닛·불필요한 소스가 남아 빌드나 후속 모델 작업에 영향을 줄 수 있다.
- **개선 방향**: rename 표시가 아니라 두 트리의 경로 집합 차이를 사용하고 삭제 실패를 전파한다. 부분 실패를 성공으로 보고하지 않는다. 안전 체크포인트와 무시 파일 보존 정책을 유지한다.
- **검증 시나리오**: 동일 내용 rename, 수정 후 rename, 잠긴 추가 파일, 읽기 전용 파일, 삭제 실패 후 복원 재시도를 확인한다.

### 15. steer/follow-up 요청에 체크포인트가 없음

- **근거**: 정적 분석 [INFERENCE]. [ChatActions:63–82](../src/RADAgent.ChatActions.pas#L63), [ChatQueue:29–57](../src/RADAgent.ChatQueue.pas#L29).
- **발생 조건·원인**: 작업 중 제출은 `QueueMessage`로 바로 반환한다. `CheckpointBeforePrompt`는 idle 일반 프롬프트 경로에만 있다.
- **영향**: 사용자가 작업 중 보낸 메시지 직전의 파일 상태가 남지 않고 복원 버튼도 연결되지 않는다. 문장 기반 재연결에서는 다른 동일 문장의 체크포인트가 잘못 붙을 여지도 있다.
- **개선 방향**: 사용자 메시지의 전송 직전 체크포인트 계약을 큐 전송에도 적용한다. 전송 시점과 실제 후속 턴 실행 시점이 다름을 명시하고, 실패한 전송을 대화 엔트리에 연결하지 않는다.
- **검증 시나리오**: steer와 follow-up을 연속 제출하고 각각의 체크포인트·엔트리 연결을 확인한다. 큐 취소·전송 실패와 02번의 세션 식별도 함께 검사한다.

### 16. 부분 문자열 교체로 폼 구조 변경 제한을 통과함

- **근거**: 정적 분석 [INFERENCE]. [FormText:176–199](../src/RADAgent.FormText.pas#L176).
- **발생 조건·원인**: `object Button1: TButton`에서 old=`Button1: TButton`, new=`Button2: TButton`을 지정한다. 검사 대상은 old/new 조각이므로 `object`가 없고, 최종 폼은 문법적으로 유효하며 속성 검사도 구조 이름을 비교하지 않는다.
- **영향**: 스트리밍 컴포넌트 이름만 바뀌고 소스 필드·참조는 디자이너 rename을 거치지 않는다. 폼과 소스가 불일치한다.
- **개선 방향**: 완성된 변경 전후 폼의 구조 선언을 비교하거나 교체 범위를 검증된 속성 값 영역으로 제한한다. 구문 파싱 성공과 의미적 안전성을 구분한다.
- **검증 시나리오**: 이름·클래스·object 키워드의 부분 교체를 거부하면서 정상적인 단일·여러 줄 속성 편집은 허용하는지 확인한다.

### 17. 이벤트 핸들러 생성이 이전 Undo 기록을 제거함

- **근거**: 정적 분석 [INFERENCE] 및 설치된 ToolsAPI 계약 확인. [HandlerCode:74–83](../src/RADAgent.HandlerCode.pas#L74).
- **발생 조건·원인**: 이벤트 연결 시 C++ 선언·본문이나 Delphi 빈 핸들러 유지 주석을 삽입한다. 공통 삽입 함수가 `CreateWriter`를 사용하며, ToolsAPI 설명상 이 writer를 해제하면 editor Undo 버퍼가 비워진다.
- **영향**: 도구가 만든 변경뿐 아니라 사용자의 이전 소스 편집도 일반 Undo로 되돌릴 수 없게 된다.
- **개선 방향**: 해당 작업을 undoable writer로 수행하고 디자이너 변경과 소스 편집의 Undo 단위를 검토한다. UTF-8 바이트 오프셋 처리 계약은 유지한다.
- **검증 시나리오**: 사용자 편집 뒤 이벤트를 생성하고 Undo한다. 도구 변경과 그 이전 사용자 편집을 기대한 순서로 되돌릴 수 있어야 한다.

### 18. C++ 함수형 이벤트 핸들러 반환형이 잘못 생성됨

- **근거**: 정적 분석 [INFERENCE]. [HandlerCode:185–205](../src/RADAgent.HandlerCode.pas#L185). 설치된 `Vcl.Forms.pas`의 `THelpEvent`는 Boolean 반환 함수다.
- **발생 조건·원인**: C++ VCL 폼의 `OnHelp`처럼 반환값이 있는 이벤트를 연결한다. `EnsureCppHandler`는 인자 RTTI는 읽지만 선언과 정의의 반환형을 항상 `void`로 작성한다.
- **영향**: 이벤트 형식과 호환되지 않는 핸들러가 소스에 추가된다. 컴파일 실패 또는 잘못된 반환값 계약으로 이어질 수 있다.
- **개선 방향**: RTTI에서 반환형을 읽고 유효한 기본 반환 본문을 생성한다. 지원하지 않는 형식은 소스를 바꾸기 전에 명확히 거부한다.
- **검증 시나리오**: 일반 procedure형 이벤트와 Boolean 반환 이벤트를 각각 생성·연결·빌드하고, 반환값이 실제 호출자에게 올바르게 전달되는지 확인한다.

### 19. C++ 진단 대상 선택이 다른 프로젝트의 성공 시간을 사용함

- **근거**: 정적 분석 [INFERENCE]. [CppDiagnostics:152–189](../src/RADAgent.CppDiagnostics.pas#L152).
- **발생 조건·원인**: A의 C++ 빌드 성공 후 B를 빌드하거나 플랫폼·구성을 바꾼다. 단일 전역 `GLastOk`와 파일 수정 시각을 비교하므로 새 대상의 오류 소스가 그보다 오래되면 진단 컴파일 대상에서 빠진다.
- **영향**: 실패 자체는 알지만 실제 오류 위치 대신 일반적인 오류 없음 안내만 돌려줄 수 있다. 모델이 빌드 문제를 수정할 근거를 얻지 못한다.
- **개선 방향**: 성공 상태를 프로젝트·구성·플랫폼별로 관리하거나 대상 정체성이 바뀔 때 무효화한다. 파일 시각만으로 구성별 오류를 배제하지 않는다.
- **검증 시나리오**: A 성공 후 수정 시각이 오래된 B의 오류, 같은 소스의 Debug/Release·Win32/Win64 차이를 검사한다.

### 20. 프로젝트 전환으로 승인 카드는 사라져도 대기는 남음

- **근거**: 정적 분석 [INFERENCE]. [ChatApprovalCard:140–147](../src/RADAgent.ChatApprovalCard.pas#L140), [ChatSession:233–238](../src/RADAgent.ChatSession.pas#L233).

- **영향**: 화면에는 카드가 없는데 내부 루프는 그 카드의 응답을 계속 기다린다. 중지·뷰 종료 등 별도 해제 동작 전까지 오래된 요청이 새 프로젝트 안에 남는다.
- **개선 방향**: 프로젝트·세션을 교체하기 전에 대기 승인을 명시적으로 취소하고 호출 스택이 안전하게 빠져나오도록 한다. 취소 뒤 변경 적용과 이전 자식에 대한 결과 전송도 막는다.
- **검증 시나리오**: IDE 도구 승인과 omp 도구 승인 각각에서 프로젝트를 전환한다. 카드 제거와 요청 종료가 함께 일어나고 새 프로젝트 입력이 정상 동작해야 한다.

### 21. 이전 프로젝트의 BTW 답변이 현재 프로젝트로 표시됨

- **근거**: 정적 분석 [INFERENCE]. [ChatBtw:193–218](../src/RADAgent.ChatBtw.pas#L193).
- **발생 조건·원인**: A에서 곁가지 질문을 시작하고 완료 전에 B로 전환한다. 저장은 `Active.ProjectDir`을 사용하지만 진행·완료 표시는 항상 현재 전역 `ChatSession`으로 보낸다.
- **영향**: A의 답이 B의 transcript와 패널에 나타난다. 그 카드에서 후속 질문을 하면 B의 디렉터리에서 주제를 찾으므로 실패할 수 있다.
- **개선 방향**: 질문의 프로젝트·세션 정체성을 표시 전달에도 적용한다. 백그라운드 완료 결과는 원래 프로젝트에 저장하되 현재 뷰가 다르면 섞어 표시하지 않는다.
- **검증 시나리오**: A 질문 → B 전환 → 진행·완료 → A 복귀 순서에서 결과의 저장·표시·후속 질문 대상이 계속 A인지 확인한다.

### 22. 전송 확인 응답이 새 초안을 지움

- **근거**: 국소 재현. [composer.js:52–79](../src/chat/composer.js#L52).
- **발생 조건·원인**: A를 보낸 뒤 호스트의 저장·체크포인트 작업과 비동기 확인이 끝나기 전에 입력을 B로 바꾼다. `submitted()`는 전송 스냅샷이 아니라 현재 input과 첨부를 지운다.
- **재현 결과**: 실제 `composer.js`를 메모리 내 DOM fixture에서 실행했다. 게시된 요청은 A뿐인데 보내지 않은 B가 비워졌다. 현재 입력을 history에 넣는 구현이므로 기록에도 B가 들어간다.
- **영향**: 후속 초안·새 첨부가 유실되고 보낸 입력 기록이 실제 전송 내용과 달라진다.
- **개선 방향·검증**: 제출 ID와 초안 revision·첨부 스냅샷을 확인 응답에 연결한다. 확인된 스냅샷만 정리한다. 지연·실패·연속 제출·확인 전 첨부 추가에서 새 사용자 입력이 보존되는지 검사한다.

### 23. 상대 파일 참조가 링크로 변환되지 않음

- **근거**: 국소 재현. [markdown.js:17](../src/chat/markdown.js#L17).
- **발생 조건·원인**: `Main.pas:42`, `src/Main.pas(42)` 같은 상대 경로를 답변에 표시한다. 정규식 리터럴의 상대 경로 분기가 단어 경계 `\b`가 아닌 literal `\\b`를 사용한다.
- **재현 결과**: 실제 renderer의 `renderInline('Main.pas:42')` 결과는 그대로 `Main.pas:42`였고 file-ref 요소가 없었다.
- **영향**: 파일 위치를 클릭해 IDE에서 여는 동작이 상대 참조에서 작동하지 않는다. 절대 드라이브 경로 분기는 별개로 동작한다.
- **개선 방향·검증**: 경계 표현을 수정하고 상대 경로·하위 폴더·줄/열 표기를 검증한다. 일반 문장 일부를 경로로 잘못 인식하지 않는지와 클릭 시 기준 디렉터리도 확인한다.

### 24. 링크 대상이 두 번 HTML 이스케이프됨

- **근거**: 국소 재현. [markdown.js:113–131](../src/chat/markdown.js#L113), [markdown.js:19–26](../src/chat/markdown.js#L19).
- **발생 조건·원인**: `&`가 있는 URL이나 파일 경로를 표시한다. 입력 전체를 먼저 escape한 뒤 추출한 URL·경로에 `escapeAttr`를 다시 적용한다.
- **재현 결과**: `[docs](https://example.com/?a=1&b=2)`의 속성이 `data-url="https://example.com/?a=1&amp;amp;b=2"`로 생성됐다. `C:\R&D\Main.pas:42`도 `data-path`에 `&amp;amp;`가 들어갔다.
- **영향**: DOM에서 읽은 실제 대상에 문자 `&amp;`가 남는다. 브라우저의 쿼리 키 또는 IDE 파일 경로가 달라진다.
- **개선 방향·검증**: raw 대상과 escaped 표시 문자열을 분리하고 속성에는 한 번만 escape한다. `&`, 따옴표, 한글·공백 경로, URL query를 확인하되 HTML 삽입 방어를 약화시키지 않는다.

### 25. 글자 대체 화면이 불러온 대화 기록을 표시하지 않음

- **근거**: 정적 분석 [INFERENCE]. [ChatFallback:49–83](../src/RADAgent.ChatFallback.pas#L49), [ChatActions:271–293](../src/RADAgent.ChatActions.pas#L271).
- **발생 조건·원인**: WebView2를 사용할 수 없는 상태에서 세션을 전환·복원한다. 처리부는 transcript를 비우고 `PageHistory`를 내보내지만 `AppendFallback`에는 `history` 분기가 없다.
- **영향**: 대화를 불러왔다는 알림만 보이고 실제 사용자·답변 기록은 빠진다. 뷰를 다시 붙여도 같은 history 프레임이 무시된다.
- **개선 방향**: 대체 화면도 history 계약을 처리하여 live user/assistant 메시지와 같은 의미의 텍스트를 렌더링한다. 빈 기록과 여러 페이지 기록의 순서를 유지한다.
- **검증 시나리오**: WebView2 없는 환경에서 새 세션·이전 세션 전환·체크포인트 복원·뷰 재부착을 확인한다.

### 26. 부분 답변이 있으면 BTW 실패를 지워 정상 완료로 저장함

- **근거**: 정적 분석 [INFERENCE]. [BtwRunner:164–173](../src/RADAgent.BtwRunner.pas#L164), [BtwRunner:216–231](../src/RADAgent.BtwRunner.pas#L216).
- **발생 조건·원인**: 곁가지 답변의 텍스트 일부가 수신된 뒤 provider 오류로 끝난다. `HandleLine`은 오류를 기록하지만 `Finish`가 텍스트가 비어 있지 않으면 `FError`를 비운다.
- **영향**: 미완성 답변이 `done`으로 저장되고 오류 원인도 표시되지 않는다. 오류가 지워진 조건에서 stderr 파일도 삭제될 수 있다.
- **개선 방향**: 부분 텍스트와 종료 성공 여부를 별도로 관리한다. 명시적인 오류·비정상 종료를 텍스트 존재만으로 성공으로 바꾸지 않는다.
- **검증 시나리오**: text_delta → error message_end → 종료 순서에서 답변 일부와 오류가 함께 남아야 한다. 정상 완료와 사용자 중지는 별도 상태로 유지한다.

### 27. 이전 턴의 중지 타이머가 다음 턴을 종료할 수 있음

- **근거**: 정적 분석 [INFERENCE]. [ChatStop:40–49](../src/RADAgent.ChatStop.pas#L40), [ChatStop:65–73](../src/RADAgent.ChatStop.pas#L65).
- **발생 조건·원인**: A 중지 후 A가 끝나고, 250ms 감시 타이머가 idle을 관찰하기 전에 B가 시작된다. 타이머는 전역 Busy만 보고 어느 턴을 중지했는지 구분하지 않는다.
- **영향**: A를 멈추려고 시작한 5초 제한이 B를 강제 종료한다. B에서 처음 누른 중지도 이전 `AbortAt` 때문에 두 번째 중지로 해석될 수 있다.
- **개선 방향**: 감시 대상을 프로세스·턴 ID 또는 적절한 시작 식별자에 묶는다. 대상 턴 종료·교체 이벤트에서 즉시 해제하고 다른 턴에는 적용하지 않는다.
- **검증 시나리오**: A 중지·종료와 B 시작을 타이머 틱 사이에 배치한다. B가 5초 이상 실행되어도 이전 감시로 종료되지 않아야 한다.

### 28. BTW가 로컬 처리 프롬프트의 완료 프레임을 무시함

- **근거**: 정적 분석 [INFERENCE]. [BtwRunner:137–180](../src/RADAgent.BtwRunner.pas#L137). RPC 계약은 로컬 완료의 `agentInvoked=false` 또는 `prompt_result`를 일반 `agent_end`와 구분한다.
- **발생 조건·원인**: 질문이 `/usage`처럼 omp가 로컬에서 처리하는 명령이다. 질문 문자열을 그대로 보내지만 `TBtwRun`은 로컬 완료와 `command_output`을 처리하지 않는다.
- **영향**: agent_end 없이 완료된 자식의 stdin을 계속 열어 둔다. ready 이후 일반 응답 타임아웃도 없어 카드가 실행 중으로 남고 후속 질문을 막을 수 있다.
- **개선 방향**: 주 대화 파서와 동일한 완료 계약을 적용하여 로컬 출력·완료를 처리한다. 성공 응답의 접수와 턴 완료를 혼동하지 않는다.
- **검증 시나리오**: `/btw /usage` 및 두 로컬 완료 형식 각각에서 결과가 표시되고 질문 상태가 종료되는지 확인한다.

## 개선 논의 순서와 공통 원칙

1. **승인·변경 경계**: 01, 03–05, 16을 먼저 다룬다. 승인한 대상·내용과 실제 적용 대상을 동일하게 유지하고, 사용자 편집과 저장 실패를 무시하지 않는다.
2. **프로세스·객체 수명**: 07–13, 20, 27을 함께 설계한다. 세대 ID, 종료 순서, 대기 승인·셸·타이머·콜백의 소유권을 하나의 일관된 정책으로 정한다.
3. **복원 정합성**: 02, 14–15를 함께 다룬다. 파일 스냅샷과 대화 엔트리의 정확한 연결, 부분 실패 처리, 기존 기록의 안전한 처리 방식을 정한다.
4. **설정·언어 동시성**: 06, 09는 사용자 설정 보존과 공유 데이터 수명 문제다. 오류를 감추는 예외 처리만 추가하는 방식은 해결책이 아니다.
5. **나머지 계약**: 이벤트 생성·Undo, C++ 진단, BTW 종료 상태, UI 입력·링크·대체 화면, 개발 스크립트를 독립적으로 개선한다.

- 수정 범위는 각 문제의 관찰 가능한 계약으로 제한한다. 이 보고서는 대규모 리팩터링을 일괄 승인하는 문서가 아니다.
- 외부 도구의 명령·응답 계약은 검증된 omp 버전과 스킬을 따른다. 없는 RPC 필드나 송신 chunk 지원을 가정하지 않는다.
- 회귀 테스트는 실패 전후 차이를 관찰할 수 있는 경계·상태 전이에 둔다. 소스 문자열이나 내부 함수 연결만 확인하는 테스트로 대체하지 않는다.
- IDE 의존 항목은 throwaway 프로젝트와 같은 비트의 호스트를 사용한다. 패키지 변경 후 Win32·Win64 빌드 및 해당 동작을 확인하되 사용자 프로젝트에 장애를 주입하지 않는다.
- 코드 반영 시에는 항목별로 수정 커밋, 실제 실행한 검증, 남은 한계를 기록한다. 제안한 검증을 실행한 검증처럼 표시하지 않는다.

## 검토 범위와 한계

- 읽은 영역: RPC 파싱·프레이밍·프로세스, 채팅 세션·승인·계획·큐·BTW, 파일 동기화·Git 체크포인트, ToolsAPI 폼·모듈·편집·컴파일·디버거, WebView2·도킹 수명, 설정·LSP·언어, 채팅 프런트엔드, 빌드·설치·서명·배포 경로와 관련 테스트.
- 최근 MCP 이름 변경은 HTML → JavaScript → ChatPageCommands → ChatExtensions의 `mcpServers`/`toggleMcpServer` 전달이 일치했다. 해당 변경에서 별도 producer/consumer 불일치를 확인하지 못했다.
- 격리 실행으로 확인한 항목은 02, 14, 22–24다. 14는 Delphi 함수를 직접 호출한 것이 아니라 같은 Git·Windows 파일 작업 순서를 실행했다. 02와 22는 실제 JS에 최소 DOM fixture를 제공한 실행이다.
- 실제 IDE 접근 위반, 패키지 언로드 중 다운로드, 번역 사전 경쟁, 네트워크 장애, 서명·설치·레지스트리 동작은 이번 검토에서 실행하지 않았다.
- 전체 화면의 시각적 배치와 다섯 언어 번역의 자연스러움을 재검수한 보고서가 아니다. C++와 구버전 IDE의 전체 조합을 실행한 결과도 아니다.
- 추가 문제가 없다는 보증은 아니다. 특히 스레드·콜백 수명 문제는 수정 후 지연·취소·전환 순서를 통제한 재현과 실제 IDE smoke 검증이 필요하다.
